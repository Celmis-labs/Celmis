## Частина 1. Деплой

### 1.1 Що з чого складається

| Сервіс | Порт (host) | Стан | Де живуть дані |
|---|---|---|---|
| `postgres` | `${POSTGRES_HOST_PORT:-5432}` | stateful | volume `postgres_data` |
| `api` (FastAPI + MCP + поллер) | `${API_HOST_PORT:-8000}` | stateless* | volumes `workspace_data`, `vault_data` |
| `web` (Next.js) | `${WEB_HOST_PORT:-3000}` | stateless | — |

\* `api` тримає зашифрований credential-store (SQLite) у `workspace_data` і
vault-нотатки у `vault_data`. Втратите ці volume — втратите ключі й індекси,
але не Postgres-дані. Бекап: [BACKUP_RESTORE.md](BACKUP_RESTORE.md).

Зовнішні залежності: **Qdrant Cloud** (вектори) і **LLM-провайдер**. Qdrant
має безкоштовний 1 GB кластер — його вистачає на кілька середніх репозиторіїв.

### 1.2 Мінімальний запуск

```bash
cp .env.example .env
# обовʼязкові: GEMINI_API_KEY, QDRANT_URL, QDRANT_API_KEY, POSTGRES_PASSWORD
# згенеруйте секрети:
python -c "import secrets; print('CELMIS_JWT_SECRET=' + secrets.token_urlsafe(48))" >> .env
python -c "import secrets; print('NEXTAUTH_SECRET=' + secrets.token_urlsafe(48))" >> .env

docker compose up -d --build
docker compose exec api alembic upgrade head   # хоча api робить це сам на старті
```

Перший зареєстрований користувач автоматично стає адміном
([auth.py](../src/api/routers/auth.py) — `is_admin=users.count() == 0`).
Зареєструйтесь одразу після підняття: доти signup відкритий для будь-кого.

Порти зайняті? `API_HOST_PORT`, `WEB_HOST_PORT`, `POSTGRES_HOST_PORT` у `.env`.
Якщо міняєте `WEB_HOST_PORT` — синхронно правте `NEXTAUTH_URL` і
`CELMIS_CORS_ORIGINS`, інакше логін мовчки ламається.

### 1.3 Що треба зробити руками після першого підняття

Це не опції — без них система не працює або працює небезпечно.

1. **Ключі LLM** — `/settings/llm`. Ключі спільні на воркспейс і доступні
   тільки адмінам; звичайний користувач із доступом до чату не може ні
   додати, ні видалити ключ. Три профілі (`chat` / `review` / `embeddings`)
   вибирають провайдера й модель незалежно.
2. **Git-конектор** — `/connections`. Токен зберігається у спільний
   workspace-слот, не на конкретного адміна (див. 1.5).
3. **`MCP_JWT_SECRET`** — окремо від `CELMIS_JWT_SECRET`, щоб ротація
   MCP-ключа не розлогінювала веб. Якщо не задати, MCP підхопить
   `CELMIS_JWT_SECRET` як fallback.
4. **Змінити `CELMIS_JWT_SECRET` з дефолту.** У compose стоїть
   `change-me-in-production`. З ним будь-хто підпише валідний токен.

### 1.4 Пошта і скидання паролів

Мейлера немає. `/forgot-password` **свідомо нічого не повертає** — токен у
відповіді неавтентифікованого ендпоінта означав би «знаю пошту → маю акаунт»
([CWE-640](https://cwe.mitre.org/data/definitions/640.html)). Замість цього:

- **Адмін видає лінк** — `/admin/workspaces`, іконка ключа біля учасника.
  Лінк копіюється в буфер, діє 15 хвилин, одноразовий. Передавайте приватно.
- **Оператор із shell-доступом** — коли єдиний адмін заблокований:
  ```bash
  docker compose exec api python -m src.cli auth reset-link user@example.com
  ```
- **Оператор без UI, у логи** — `AUTH_RESET_LINK_TO_LOG=true` (default off).
  Вмикайте тільки якщо логи не їдуть в агрегатор.

Скидання пароля **не логінить** і **відкликає всі refresh-токени** — щоб
скидання виганяло зловмисника, а не працювало паралельно з ним.

Це той самий підхід, що у Metabase, GitLab, Gitea і authentik. Хочете
самообслуговування — вмикайте SMTP; тоді OWASP-вимога про side-channel
виконується і адмін з ланцюжка зникає.

### 1.5 Git-токени: workspace, а не персональні

Токени резолвляться за трьома рівнями
([git_keys.py](../src/credentials/git_keys.py)):

```
tier 0  workspace   ← сюди пишуться всі нові токени
tier 1  <user_id>   ← read-only back-compat
tier 2  default     ← легасі CLI-слот
```

**Чому це важливо.** Раніше токен належав тому адміну, який натиснув
«Зберегти». Людина йде з компанії → її PAT починає віддавати 403 → поллер
пропускав її репозиторії з debug-логом. Ніхто про це не дізнавався.

Міграція наявних інсталяцій — явна дія, не автоматична (копіювати креденшли
мовчки не можна, це змінює від чийого імені система діє на git-хостингу):

```bash
docker compose exec api python -m src.cli auth migrate-git-tokens            # план
docker compose exec api python -m src.cli auth migrate-git-tokens --apply    # виконати
```

Старий рядок лишається; видаліть його вручну коли переконаєтесь.

**Наступний крок — GitHub App замість PAT.** Дає 1-годинні installation-токени
замість річних, ліміт до 12 500 req/год замість спільних 5 000 (спільних із
Copilot і будь-яким іншим інструментом того користувача), і коментарі від
`@celmis[bot]` замість імені живої людини. Вебхуки для App
[опційні](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app) —
зніміть галочку *Active*, і наш поллер працює далі без публічного ingress.
[Manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest)
дає onboarding в один клік (так робить Atlantis).

> ⚠️ **Bitbucket app passwords вимкнено з 2026-07-28.**
> [Графік brownout](https://community.atlassian.com/forums/Bitbucket-articles/Deprecation-notice-Bitbucket-Cloud-app-password-brownout/ba-p/3237429).
> Під час brownout API віддає 401, git-over-HTTPS — 410. Наш
> [connections.py](../src/api/routers/connections.py) приймає саме email +
> app password. Мігруйте на
> [workspace/repository access token](https://support.atlassian.com/bitbucket-cloud/docs/using-access-tokens/).

### 1.8 Під які архітектури збирається образ

`amd64` і `arm64` — обидві нативно. Це не дрібниця: у 1.6 рекомендовані саме
ARM-хости (Oracle Ampere A1, Hetzner CAX), а `Dockerfile` доти тягнув
`osv-scanner_linux_amd64` за прямим імʼям. Завантаження проходило, сума
збігалася, і білд падав аж на `osv-scanner --version` з `exec format error` —
тобто задокументований сетап не збирався взагалі.

Два пінованих бінарники всередині образу:

| Бінарник | Стадія | Пін | Де взяти суми |
|---|---|---|---|
| `uv` | builder | `UV_VERSION` + `UV_SHA256_AMD64` / `UV_SHA256_ARM64` | `.sha256` поруч з кожним артефактом релізу astral-sh/uv |
| `osv-scanner` | runtime | `OSV_SCANNER_VERSION` + `OSV_SCANNER_SHA256_AMD64` / `_ARM64` | один `osv-scanner_SHA256SUMS` на реліз |

Правила:

- версію і **обидві** суми міняємо одним комітом. Інакше білд впаде на
  `sha256sum -c` на одній із платформ — і, за законом підлості, не на тій, де
  ви його щойно ганяли;
- невідомий `TARGETARCH` (зокрема **порожній** — так буде на legacy-білдері
  без BuildKit) зупиняє білд із явним повідомленням. Це навмисно: підстановка
  amd64 «за замовчуванням» і є та сама помилка, що дала образ, який не міг
  запустити власний сканер;
- `uv` ставиться з релізного архіву, а не через `curl … install.sh | sh`. Той
  самий патерн — виконання скрипта під час встановлення — наш власний аудит
  залежностей позначає як ризик у npm-пакетах; тримати це правило назовні й
  порушувати всередині не можна.

Крос-збірка (`docker buildx build --platform linux/arm64` з x86-машини)
працює так само, але обидва деплой-гайди збирають **на самій коробці**, тож
`TARGETARCH` там і так дорівнює архітектурі хоста.

## Частина 2. Тести

Три рівні, різна вартість, різна частота.

### 2.1 Unit — швидкі, герметичні, на кожен коміт

```bash
.venv/bin/python -m pytest -q
```

**Поточний стан: 999 passed, 8 skipped, 22 deselected, ~8 хв.**

`addopts = "-m 'not integration'"` — тести з реальною мережею відключені за
замовчуванням. Увімкнути: `pytest -m integration`.

Конфіг у [pyproject.toml](../pyproject.toml). `pytest` живе у dev-екстра
(`pip install -e '.[dev]'`) і **свідомо не входить в образ** — тому unit-тести
запускаються на хості, а не в контейнері.

Дві пастки, на які вже наступали:
- **Порядок тестів має значення.** `JwtConfig.from_env()` має fallback на
  `CELMIS_JWT_SECRET`, тому тест «немає секрета» мусить чистити **обидві**
  змінні. Інакше він проходить наодинці й падає у повному прогоні.
- **Тести, що фіксують точний список** (egress-allowlist) — це навмисно:
  додати новий напрямок мережевого трафіку не можна непомітно, тест і
  `Settings` мають мінятись одним комітом.

### 2.2 E2E — потребують піднятого стеку

```bash
./scripts/e2e.sh              # усе, що не потребує креденшлів
./scripts/e2e.sh access qa    # підмножина
```

`tests/` не запікається в образ (не варто відвантажувати тестові фікстури в
прод), тому скрипт бind-моунтить його у тимчасовий контейнер у мережі стеку.

| Скрипт | Що покриває |
|---|---|
| [access.py](../tests/e2e/access.py) | glob-матчинг, deny-wins, рівні видимості `none/metadata/code` |
| [qa.py](../tests/e2e/qa.py) | ретривал дотримується правил доступу (embed + Qdrant замокані, доступ справжній) |
| [mcp_tools.py](../tests/e2e/mcp_tools.py) | MCP-інструменти застосовують ті самі правила, що й API |
| [mcp_review_tools.py](../tests/e2e/mcp_review_tools.py) | `route_incident`, `bootstrap_client`, `migrate_consumers` загейчені |
| [reset.py](../tests/e2e/reset.py) | скидання пароля не є шляхом до захоплення акаунта |
| [gitcreds.py](../tests/e2e/gitcreds.py) | git-токени резолвляться workspace-first і переживають звільнення власника |

`reset.py` міняє реальний пароль — направляйте на одноразовий акаунт
(див. [tests/e2e/README.md](../tests/e2e/README.md)).

Кожен скрипт прибирає за собою і на вході, і на виході — перезапуск після
падіння безпечний.

**Правило, вистраждане на практиці:** ніколи не лишайте тестові дані у
продуктових таблицях. Один раз синтетичні рядки в `llm_spend` виглядали як
реальні витрати на Claude і зʼїли час на розслідування.

## Частина 3. Бенчмарки

Тести кажуть «не зламано». Бенчмарки кажуть «наскільки добре». Це окрема
інфраструктура, і без неї будь-яка зміна промпту чи моделі — здогадка.

### 3.1 Спершу: чому не вірити опублікованим цифрам

Вендорські бенчмарки суперечать один одному. Greptile ставить собі 82% і
CodeRabbit 44%; незалежний [Martian CRB](https://codereview.withmartian.com/)
ставить CodeRabbit №1 з 51.2% F1. Академічні бенчмарки дають 15–31% detection.

Різниця не в моделях — у визначенні ground truth. Вендор рахує true positive
як «розробник щось змінив після нашого коментаря»; академія — як «чи знайшло
те, що позначив живий рецензент». Оберіть одне визначення й ніколи не
порівнюйте через межу.

### 3.2 Датасети

| Датасет | Що дає | Ліцензія |
|---|---|---|
| [Martian CRB](https://github.com/withmartian/crb) | 50 PR з golden-коментарями + готовий пайплайн. **Найшвидший старт** | MIT |
| [AACR-Bench](https://github.com/alibaba/aacr-bench) | 200 PR, розмічені за глибиною контексту: Diff 754 / File 518 / Repo 233. **Єдиний спосіб виміряти чи окупається граф** | open |
| [SWE-PRBench](https://huggingface.co/datasets/foundry-ai/swe-prbench) | 350 PR, 3 заморожені конфіги контексту, таксономія Type1/2/3 | CC BY 4.0 |
| [SWR-Bench](https://arxiv.org/html/2509.01494v1) | 500 PR з дефектами + **500 чистих**. Чисті — єдиний спосіб міряти false-positive rate | див. репо |
| [c-CRAB](https://arxiv.org/abs/2603.23448) | конвертує коментарі рецензентів у **виконувані тести** — обʼєктивний оракул без LLM | див. репо |

Для security-агента: [VulnGym](https://github.com/Tencent/VulnGym) (CC BY 4.0,
3-рівневий file:line оракул, 96.3% аудитовано вручну),
[CWE-Bench-Java](https://github.com/iris-sast/cwe-bench-java) (MIT).

**Не беріть** Juice Shop / WebGoat / DVWA — немає машиночитаного file:line
ground truth і тисячі публічних walkthrough у тренувальних даних. **Не беріть**
OWASP Benchmark як корпус (мітки в іменах файлів: `CWE89_SQL_Injection__*`) —
але вкрадіть його методику: per-category TPR/FPR і **Youden's J = TPR − FPR**
як headline-метрику.

Контамінація не абстрактна: StarCoder2-7B дає 68.26% F1 на BigVul і **3.09%**
на PrimeVul — та сама задача, але дедупліковано й з виправленими мітками.

**Найцінніше — намайнити власні PR.** `GET /repos/{owner}/{repo}/pulls/comments`
віддає `path`, `line`, `diff_hunk`, `body` — тобто коментар разом із кодом, на
який він вказував. Фільтруйте до змерджених PR із змістовними коментарями,
викидайте ботів, `LGTM` і чисті ніт-піки. 150–200 позицій за день роботи, нуль
контамінації, ваші мови й конвенції.

### 3.3 Що міряти

**Головна метрика ревʼю — recall проти списку відомих дефектів, суддя відповідає
бінарно на кожен дефект окремо:** «чи згадує ревʼю проблему I? так/ні».
Холістична оцінка «постав 1–5» на коді дає κ 0.3–0.6; покривальне бінарне
судження — κ 0.71–0.87. Ті самі моделі, інше питання.

Зараховуйте влучання тільки якщо **file і line теж правильні** — саме це бачить
користувач.

Що вести окремо, ніколи не змішуючи в одне число:
- recall, **розбитий за глибиною контексту** (Diff / File / Repo) — це ROI графа
- precision, і **false-positive rate на чистих PR**
- **fabrication rate** (посилання на неіснуючий код) — жорсткий гейт, ціль ~0
- коментарів на PR (обсяг) — висока precision при трьох коментарях означає
  пропущене покриття, а не точність
- атрибуція по агентах — потрібна для абляцій
- вартість і латентність на ревʼю

Практичні пороги з індустрії: <10% FP — розробники читають усе; 10–30% —
«шумно»; >30% — тріажать із підозрою; >50% — ігнорують за замовчуванням.

**На боці Q&A найдешевша метрика вже реалізована й не виміряна:**
[citations.py](../src/qa/citations.py) — `verify_citations()` віддає
`ok / missing_file / bad_line / unknown_repo / not_in_context`. Детерміновано,
безкоштовно, ловить найгірший режим відмови (авторитетна мертва цитата).
Достатньо зробити з нього гейт: `citations_invalid == 0`.

Далі — file-level recall@k, де gold-набір безкоштовно береться з `git log`
(коміт → змінені файли), рахується через [ranx](https://github.com/AmenRa/ranx).

### 3.4 LLM-суддя

Канонічні «85% згоди з людьми» (MT-Bench) роздуті випадковим збігом:
дослідження на 21 судді й ~541k суджень показало 33–41 в.п. дефляції каппи.
Суддя з «85% agreement» може бути суддею з κ≈0.45. **Завжди звітуйте κ, ніколи
голу згоду.**

Код — окремо слабке місце: на CodeJudgeBench сама лише перестановка кандидатів
місцями зсуває точність до 11 в.п.

Конфігурація:
- **reasoning-модель з іншої родини**, ніж та, що під тестом (self-enhancement
  bias дає +10…+25 в.п. на користь своєї родини)
- **T=0**, зафіксований снапшот моделі, і все одно K≥3 повтори
- **бінарні декомпоновані критерії**, не Лікерт 1–5
- для попарних порівнянь — **обидва порядки**, зараховувати тільки узгоджені
  вердикти; частка нічиїх і є вашим показником position bias
- панель із 3 маленьких моделей **різних провайдерів** б'є одного великого
  суддю при ~7× меншій вартості: зсуви провайдер-специфічні й взаємно гасяться

Калібрування: розмітьте ~200 прикладів руками. **κ ≥ 0.6 щоб запускати,
κ ≥ 0.8 щоб гейтити.** Перевіряйте 50 на місяць на дрейф.

### 3.5 Розмір golden-набору

Порівнюйте **парно** — той самий набір на обох версіях, критерій Макнемара.
Потужність дає тільки кількість розбіжних пар.

| n (парно) | MDE при 20% розбіжностей |
|---|---|
| 100 | 12.4 в.п. |
| **200** | **8.8 в.п.** |
| **300** | **7.2 в.п.** |
| 500 | 5.6 в.п. |

Непарно, при базі 70% і потужності 80%, щоб побачити падіння на 5 в.п. треба
**1374 приклади на групу**. Парність дає медіанне скорочення в 2.15×.

**Практична відповідь: 300–500 PR** → 5–7 в.п. MDE. Набір з 50 позицій дає
±13 в.п. на одному прогоні — він **не бачить** регресії на 5 в.п., не вдавайте
що бачить.

Три речі, без яких цифри брешуть
([Anthropic, Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640)):
- **Кластеризуйте похибку по репозиторію.** PR з одного репо не незалежні; на
  DROP кластеризовані SE вийшли **у 3.05× більші**. Ваші довірчі інтервали
  потроюються — і це чесна цифра.
- **K повторів на позицію:** K=2 зрізає дисперсію на ⅓, K=4 — вдвічі, після
  K≈5 виграш зникає.
- **Спершу зміряйте шумовий поріг:** той самий конфіг 3 рази, розподіл дельт.
  Публікуйте його поруч із кожним результатом. Нижче порогу — не регресія.

Множинні порівняння: 1–2 гейтові метрики при α=0.05 без корекції, решта під
Benjamini–Hochberg FDR q=0.10. Бонферроні на корельованих метриках перекорегує.

### 3.7 План на 4 дні

**День 1 — свій ground truth.** Намайнити `pulls/comments` по своїх репо,
150–200 позицій. Паралельно склонувати Martian CRB — 50 PR і робочий пайплайн
безкоштовно.

**День 2 — Layer 0, детерміновано, без LLM.** `tests/eval/` під маркером `eval`.
Ревʼю: чи є знахідка на ground-truth `(path, line)`. Q&A: recall@k із `git log`
через `ranx`; `verify_citations()` → 0 невалідних. Хвилина на прогін, ловить
більшість реальних регресій.

**День 3 — суддя.** Тільки покривальне бінарне судження. T=0, зафіксований
снапшот, Pydantic-схема відповіді, кеш. Тристороння класифікація незіставлених
коментарів: CONFIRMED / PLAUSIBLE / FABRICATED (не зливайте останні два — так
ви оптимізуєте геть справжні знахідки). Розмітьте 50 суджень руками, порахуйте
κ, **не рухайтесь далі при κ < 0.6**.

**День 4 — регресійний харнес.** Макнемар кандидат-vs-базлайн на тому самому
наборі, кластеризовано по репо. Той самий конфіг 3 рази — шумовий поріг. У CI
щоночі, гейт на 1–2 метриках.

**Перший справжній експеримент — абляція контексту на своїх даних:**
diff-only vs diff+граф vs full-context.

Три незалежні джерела кажуть, що **більше контексту робить ревʼю гіршим**. На
SWE-PRBench усі 8 фронтир-моделей деградують монотонно diff-only → diff+file →
full-context; 2000-токенний структурований diff обійшов 2500-токенний
full-context з AST та import-графом на **кожній** моделі. GitHub отримав те
саме на Copilot review — повернення промпта до diff зрізало вартість на ~20%
без втрати якості.

Якщо це справджується й у нас — це найцінніша знахідка, яку харнес взагалі
може дати, і дізнатись про неї треба **до** масштабування графа, а не після.
