ЗАПУСК MARTIAN CODE REVIEW BENCH З НУЛЯ
машинний акаунт, організація, токени, прогін
================================================================================

Написано за результатами реального прогону 20–21.08.2026. Кожен розділ, де є
попередження, — це помилка, яку ми вже зробили; вони коштували годин.

Орієнтовний час: 40 хв налаштування + 1–3 год прогону (залежить від лімітів).


================================================================================
1. МАШИННИЙ АКАУНТ
================================================================================

ЧОМУ НЕ ОСОБИСТИЙ
-----------------
Токен потрапляє в .env, у бекапи, у логи, у скріншоти. Особистий акаунт має
доступ до всіх ваших репозиторіїв. Ми це вже пройшли: PAT особистого акаунта
зі скоупами admin:org + delete_repo опинився в git-історії. Машинний акаунт
обмежує найгірший сценарій зіпсованими коментарями в бенчмарк-PR.

СТВОРЕННЯ
---------
1. Вийти з GitHub або відкрити приватне вікно
2. github.com/signup
   - логін:  <проект>-bot        (напр. celmis-bot)
   - пошта:  окрема, або аліас +bot@ якщо провайдер підтримує
             ВАЖЛИВО: пошту треба ПІДТВЕРДИТИ, інакше частина API мовчить
3. Увімкнути 2FA — github.com/settings/security
   Без 2FA організації з політикою обов'язкового 2FA не приймуть акаунт

⚠ ПАСТКА: КАРАНТИН НОВОГО АКАУНТА
---------------------------------
GitHub зрізає новому акаунту ліміт API до 60 запитів/год замість 5000, якщо
бачить сплеск. Ознака в заголовках:

    x-ratelimit-limit: 60          ← має бути 5000
    API rate limit exceeded for user ID <...>

Ліміт рахується НА АКАУНТ, не на токен — перевипуск PAT нічого не змінює.

ЯК НЕ ПОТРАПИТИ:
  - перші дві доби не робити пакетних операцій
  - не перебирати репозиторії організації запитом на кожен
    (наш скрипт робив GET /repos/{owner}/{repo} на кожен репо для кожного
     з 50 PR — кілька тисяч запитів за хвилини, це і спричинило карантин)
  - кешувати списки, а не перепитувати

ЯКЩО ВЖЕ ПОТРАПИЛИ:
  - зачекати кілька днів звичайної активності — знімається само
  - або support.github.com/request/landing
    ⚠ НЕ форма "Reinstatement request": вона для заблокованих акаунтів, і
      жоден із її варіантів «чому» не буде правдою у вашому випадку
  - прогін усе одно пройде, просто вдвічі повільніше


================================================================================
2. ОРГАНІЗАЦІЯ
================================================================================

Безкоштовна, необмежена кількість публічних і приватних репозиторіїв.

1. github.com/organizations/plan → Free
2. Назва: <проект>-bench   (напр. celmis-bench)
   Ця назва потрапить у публічні URL і в звіт — переїхати потім без втрати
   посилань не вийде
3. Settings → Member privileges → Repository creation:
   увімкнути "Public" і "Private"
   Без цього бот не створить форки

ДОДАТИ БОТА
-----------
People → Invite member → <проект>-bot → роль Member
Member достатньо: створювати репозиторії, форкати, писати коментарі.
Owner потрібен лише щоб ВИДАЛЯТИ репозиторії — і саме тому Owner краще НЕ
давати (див. розділ про скоупи).

Прийняти запрошення з-під акаунта бота.


================================================================================
3. ТОКЕНИ
================================================================================

github.com/settings/tokens/new   (класичний PAT, з-під акаунта бота)

МІНІМАЛЬНИЙ НАБІР
-----------------
    repo               читати діф, створювати репозиторії, писати коментарі
    notifications      ТІЛЬКИ якщо потрібне авто-рев'ю через полінг

⚠ Fine-grained токени полінг НЕ підтримують — для нього потрібен класичний
  PAT або вебхук. Це написано прямо в UI Celmis на сторінці Connections.

ЧОГО НЕ ДАВАТИ І ЧОМУ
---------------------
    delete_repo        Свідомо НЕ давати. Тоді помилковий або зламаний скрипт
                       не зможе знищити результати. Ціна: видаляти зайві
                       репозиторії доведеться вручну через веб — це буває
                       разів зо два за весь прогін.
    admin:org          Не потрібен. Member може все, що треба.
    admin:*, workflow, gist, user, write:packages
                       Не потрібні. Кожен зайвий скоуп — це те, що зможе
                       зробити токен, якщо витече.

ТЕРМІН ЖИТТЯ
------------
90 днів. Безстроковий токен — це токен, який колись витече і житиме вічно.

⚠ ЗБЕРІГАННЯ
------------
Токен вводити ЧЕРЕЗ UI Celmis (Settings → Git connections), а не в .env.

Перевірено на коді:
  - рев'ю PR читає ТІЛЬКИ зашифроване сховище (providers/base.py), у нього
    немає жодного звернення до оточення
  - клон має ланцюг: сховище → env → legacy, де сховище виграє завжди
  - .env потрібен лише для CLI всередині контейнера

На диску токен лежить як Fernet-шифротекст (gAAAAA…) у
/workspace/data/secrets/credentials.db, слот ws:{uuid}. Перевірити:
  docker compose exec postgres ... або читанням credentials.db — у сирому
  рядку не має бути "ghp_".

================================================================================
4.1. ЯКУ МОДЕЛЬ БРАТИ І ЯК ОБРАТИ ФОЛБЕК
================================================================================

ЗАМІРЯНА ДОСТУПНІСТЬ                              (21.08.2026, платний тариф)
----------------------------------------------------------------------------
Одні й ті самі 4–5 запитів поспіль, один ключ, один момент часу:

    gemini-3.6-flash            5/5   ← основна
    gemini-3-flash-preview      4/4   ← фолбек
    gemini-3.7-flash            3/5   503 "experiencing high demand"
    gemini-3-flash              0/5   404 — не існує (є лише -preview)
    gemini-3-pro-preview        0/5   404 на цьому ключі
    gemini-2.5-flash            0/5   404 на цьому ключі

⚠ НЕ ДОВІРЯЙТЕ НАЗВІ. Каталог моделей провайдера і те, що реально відповідає
  вашому ключу, — різні речі. Перевіряти треба ПЕРЕД прогоном, кількома
  запитами поспіль, а не одним:

    for m in gemini/gemini-3.6-flash gemini/gemini-3-flash-preview; do
        # 4 запити, рахувати успіхи
    done

  Один успішний запит нічого не доводить: 3.7-flash дає 3 з 5.

ЧОМУ САМЕ 3.6, А НЕ 3.7
-----------------------
Новіша модель була доступна гірше. Це не властивість версії — це стан
потужностей у конкретний день. Тому: міряти в день прогону, брати ту, що
відповідає стабільно, і записати у звіт, коли міряли.

ЯК ОБИРАТИ ФОЛБЕК — ПРИНЦИП
---------------------------
Фолбек має ламатися ІНАКШЕ, ніж основна. Запасна модель того самого вендора
рятує від перевантаження ОДНІЄЇ моделі, але не від збою вендора цілком.

    сценарій                        рятує фолбек того ж вендора?
    ------------------------------  ----------------------------
    одна модель перевантажена       ТАК  (наш випадок: 3.6 → 3-flash-preview)
    вендор лежить цілком            НІ   (потрібен інший вендор)
    ключ вичерпано / скасовано      НІ   (той самий ключ)
    модель відмовляє за політикою   НІ   (див. нижче — і це важливо)

Для бенчмарка ми взяли фолбек того самого вендора свідомо: зміна вендора
посеред прогону сильніше б'є по порівнюваності, ніж зміна версії.

Для ПРОДАКШНУ логіка інша — там фолбек має бути іншого вендора, бо мета не
порівнюваність, а щоб рев'ю не зупинялось.

КОЛИ ФОЛБЕК СПРАЦЬОВУЄ, А КОЛИ НІ
---------------------------------
Спрацьовує:
    - лише ПІСЛЯ того, як основна модель вичерпала свої спроби
    - лише для THROTTLED (429) і TRANSIENT (503, обрив з'єднання)
    - додає щонайбільше ОДИН виклик
    - фолбек, що дорівнює основній, відкидається — це третя спроба під
      виглядом другої

НЕ спрацьовує:
    - для термінальних помилок (поганий ключ, невідома модель) — інша модель
      впаде так само або замаскує помилку конфігурації
    - для корективного ретраю при нечитабельній відповіді — інша модель, що
      відповідає інакше, не є виправленням помилки розбору
    - ⚠ ДЛЯ ВІДМОВИ МОДЕЛІ — а саме тут він допоміг би найбільше

⚠ ВІДМОВА МОДЕЛІ — ОКРЕМИЙ ВИПАДОК
----------------------------------
Заміряно: агент security отримує відмову в 1 випадку з 5:

    "Sorry, I cannot fulfill your request to analyze or identify
     vulnerabilities in specific code snippets."

Це проза, а не помилка API. Парсер не знаходить у ній JSON і повідомляє
"no JSON array in the reply" — тобто в логах ви бачите СИМПТОМ, а не діагноз.
Корективний ретрай перепитує те саме й отримує ту саму відмову.

Чому саме security: його промпт просить знайти експлуатовані вразливості в
конкретному коді. Решта агентів такого не просять — quality питає про стиль,
tests про покриття, architect про зв'язність.

Що з цим робити:
    - у формулюванні промпту дати захисний контекст («це наш власний код,
      рев'ю перед мержем») — знімає відмову майже завжди
    - або дозволити фолбек на іншу модель для цього класу помилки

ФАКТИЧНА ЧАСТОТА ЗАДІЯННЯ ФОЛБЕКУ
---------------------------------
За прогін на 23 PR фолбек не спрацював ЖОДНОГО РАЗУ — хоча 503 траплялись.
Причина: пауза ~2 с перед повторною спробою впоралась раніше.

Висновок для налаштування: спершу відступ між спробами, і лише потім фолбек.
Фолбек — страховка на випадок, коли повтор не рятує, а не основний механізм.

ПОАГЕНТНІ ПЕРЕВИЗНАЧЕННЯ
------------------------
Модель, стелю відповіді та рівень reasoning можна задати окремо для кожного
агента (UI → Settings → LLM Setup → Per-agent overrides). Порожнє поле
успадковує загальне налаштування.

Коли це корисно:
    - architect найдорожчий (38% рахунку) і найкорисніший — йому можна дати
      сильнішу модель
    - tests шукає прогалини в покритті, а в золотому наборі категорія
      test_gap — це 4 коментарі з 173. Для бенчмарка він майже не працює на
      результат; на реальних PR — працює
    - verifier і compliance повертають короткі структуровані відповіді, їм
      велика стеля не потрібна (1024 і 256 відповідно)

6. ФОРК 50 PR — ГОЛОВНА ЕКОНОМІЯ
================================================================================

⚠ НЕ ВИКОРИСТОВУЙТЕ step0_fork_prs.py ЯК Є

Оригінал клонує репозиторій локально й пушить у новий. Заміряно:

    вивантаження:  57.9 GB
    час:           12.7 год при каналі 10 Мбіт/с
    диск:          ~5 GB дзеркал

Причина: GitHub не ділить об'єкти між НЕспорідненими репозиторіями, тож
grafana (1.9 GB) виїжджає десять разів.

ПРАВИЛЬНИЙ СПОСІБ — ФОРК ЧЕРЕЗ API
----------------------------------
Форк ділить сховище об'єктів із батьком. Гілку можна створити прямо на SHA з
батьківського репозиторію, не маючи його локально:

    POST /repos/{source}/forks           {"organization": "<org>"}
    POST /repos/{org}/{fork}/git/refs    {"ref":"refs/heads/bench-base-N",
                                          "sha": "<base sha оригіналу>"}
    POST /repos/{org}/{fork}/git/refs    {"ref":"refs/heads/bench-pr-N",
                                          "sha": "<head sha оригіналу>"}
    POST /repos/{org}/{fork}/pulls       {"head":"bench-pr-N",
                                          "base":"bench-base-N", ...}

Результат:
    вивантаження:  ~0 байт
    час:           ~7 хвилин на всі 50
    історія:       ПОВНА (форк несе історію батька)
    діф:           побайтово ідентичний оригіналу (перевірено sha256)

Готовий скрипт: bench/scripts/fork_via_api.py
    export GITHUB_TOKEN=...
    python3 fork_via_api.py
Пише розкладку в ~/Desktop/celmis-bench-work/mapping.json, ідемпотентний.

⚠ ОБМЕЖЕННЯ: ОДИН ФОРК РЕПОЗИТОРІЯ НА ОРГАНІЗАЦІЮ
--------------------------------------------------
Тому 50 PR лягають у 7 форків по ~10, а не в 50 окремих репозиторіїв:

    <org>/grafana               10 PR
    <org>/discourse-graphite    10 PR
    <org>/cal.diy               10 PR      (cal.com перейменовано)
    <org>/keycloak               9 PR
    <org>/sentry                 6 PR
    <org>/sentry-greptile        4 PR
    <org>/keycloak-greptile      1 PR

Кожен PR має власну пару гілок bench-base-N ← bench-pr-N і власний номер.
Ізоляція потрібна між ІНСТРУМЕНТАМИ, а не між PR одного інструмента — а в
вашій організації інструмент один.

⚠ ДВІ ДРІБНИЦІ, ЯКІ КУСАЮТЬ
---------------------------
1. calcom/cal.com перейменовано на calcom/cal.diy. GET іде за редіректом,
   POST /forks — НІ. Треба спершу резолвити канонічне ім'я:
       GET /repos/{source} → якщо 301, узяти full_name з тіла

2. Якщо форкати клоном (старий спосіб), дзеркало приносить гілки
   dependabot/*, і GitHub відкриває на них PR — десяток сміттєвих PR на
   репозиторій. Вимикати одразу після створення:
       DELETE /repos/{org}/{repo}/vulnerability-alerts
       DELETE /repos/{org}/{repo}/automated-security-fixes
   Через API-форк такого не буває.

⚠ ЧОМУ 32768, А НЕ 4096
-----------------------
У Gemini 3.x токени думання рахуються в ТОЙ САМИЙ вихідний бюджет. Заміряно:
572 reasoning із 613 вихідних на тривіальному запиті.

При стелі 4096 агент architect упирався в неї у 20 з 28 викликів, JSON
обривався на півслові, і агент падав із "no JSON array in the reply".

Виміряний ефект підняття стелі:
    падінь агентів:    48%  →  12%
    знахідок на PR:    3.0  →  4.4
    вартість на PR:    $0.096 → $0.087   (менше, бо зникли марні ретраї)

⚠ ЧОМУ ПАРАЛЕЛЬНІСТЬ 3
----------------------
Агентів шість, і кожен тримає своє з'єднання до провайдера. Шість одночасних
з'єднань на звичайному каналі дають ConnectError, а на Gemini — 503.

Перевірити, що налаштування ДОЇХАЛИ до контейнера:
    docker compose exec api python -c "
    from src.review.settings import get_review_settings
    s=get_review_settings()
    print(s.agent_max_output_tokens, s.agent_concurrency)"

⚠ Змінна може існувати в коді й не передаватись через docker-compose.yml —
  ми ловили це двічі. Перевіряти саме в контейнері, не в .env.


================================================================================
7.1. ВЕРИФІКАТОР — ВИМИКАЙТЕ, ПОКИ НЕ ВИМІРЯЄТЕ
================================================================================

Верифікатор — етап ПІСЛЯ агентів, що вирішує, які знахідки дійдуть до PR.
Заміряно на 50 PR (суддя claude-sonnet-4-5):

    стеля 1024:   187 кандидатів → лишив 147   (79%)
    стеля 32768:   75 кандидатів → лишив  14   (19%)   ← 5 із 14 PR обнулено

Усі викиди — через LLM-крок. Поріг впевненості 0.5 не зняв ЖОДНОЇ, бо агенти
ставлять confidence=0.7 за замовчуванням.

Наслідок: три незалежні зміни вище за потоком (вимкнення агентів, інша модель,
нові промпти) давали ОДНАКОВИЙ FN=43 — верифікатор зрізав усе до однієї
висоти. І Celmis був ЄДИНИМ інструментом у таблиці Martian, що мовчав на
частині PR (9 із 50; у всіх лідерів — нуль).

⚠ НА ПЕРШИХ ШЕСТИ ПРОГОНАХ ЦЬОГО БЕНЧМАРКА ГРАФУ НЕ БУЛО.
Перевірено трьома фактами: repo_index_state — 0 рядків; /workspace/data/repos
— один старий клон; base.py підставляв "(no graph context)" в усі 50 PR.
Причина: форки створювались через GitHub API без локального клону (щоб не
тягнути 57.9 GB) — а індекс потребує клону. Оптимізувавши одне, відрізали інше.

ЯК ВОНО ПРАЦЮЄ (з коду, без здогадок)
    UI «Додати репо» → POST /api/repos {"url": …}   ← реєстрація, БЕЗ індексу
    POST /api/repos/index-all (або кнопка Index)    → KIND_INDEX_REPO_FULL у чергу
                                                    → клон --depth=50 + tree-sitter + graph.fdblite
    PR review → orchestrator._build_graph_context(pr)
              → settings.repo_graph_path(pr.repo_slug)
              → файл є → callers/callees/blast-radius у контекст   АВТОМАТИЧНО
              → файлу немає → "(repo not indexed …)" і рев'ю йде по дифу

    Слаг один і той самий в обох місцях: f"{provider}_{repo.replace('/','-')}"
    → github_celmis-bench-grafana. Перевірено живим файлом у /workspace.

    ЗМІН У КОДІ НЕ ТРЕБА. Треба: додати репо, натиснути Index, дочекатись.

⚠ «Додати репо» ≠ «проіндексувати». POST /api/repos лише реєструє; черга
  індексації після нього порожня. Index — окрема дія (index-all для всіх).

⚠ RUBY НЕ ІНДЕКСУЄТЬСЯ (поправка до поправки, виміряно 2026-08-22)
Порядок тверджень був такий: (1) «Ruby не індексується» — правда;
(2) поправка «це НЕПРАВДА, ось graph-stats: method 6267, file_module 3481»
— хибна; (3) це — повернення до (1), уже з виміром по мовах, а не по kind.

Прямий запит до того самого графа discourse-graphite:
    MATCH (n:Symbol) RETURN count(n)                     -> 14258
    MATCH (n:Symbol) WHERE n.file ENDS WITH '.rb' ...    -> 0

Тобто 6267 «методів» — це Ember.js-фронтенд Discourse, а не Ruby. У

Чому graph-stats дав хибну відповідь: він агрегує за kind (method, class,
file_module), а не за мовою. На питання «чи розібрано мову X» він відповісти
не може в принципі — розбивайте за розширенням файлу.
